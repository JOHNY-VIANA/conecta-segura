GUIA TÉCNICO PARA A EQUIPE

Conecta Segura

A publicação no GitHub Pages é estática e começa em demonstração. Nenhuma mensagem automática é enviada sem servidor, autenticação e provedores configurados. Abrir SMS ou WhatsApp manualmente prepara um rascunho real: a pessoa confirma o envio no aplicativo correspondente.

Executar e publicar

Use Node.js 24. Os comandos funcionam em Windows, Linux e macOS.

npm ci --ignore-scripts
npm test
npm run build
npm run validate
npm start

Aplicativo completo: http://localhost:3000. Para a versão estática:

npm run build:pages
npm run preview:pages

O preview usa http://localhost:4173/conecta-segura/. Somente dist-pages/ é publicada pelo workflow, automaticamente em pushes para main ou manualmente em Actions. O backend permanece no repositório para implantação futura.

Conectar os serviços

  1. Implante o backend real com HTTPS e SQLite ou D1/DB. Aplique a migração drizzle/0000_alerts.sql. O servidor npm start é apenas local.
  2. Configure no backend FIREBASE_PUBLIC_CONFIG, com a configuração pública do Firebase Web. Ative Google/Phone e autorize o domínio do frontend. O acesso por telefone exige reCAPTCHA e código SMS.
  3. Configure ALLOWED_ORIGINS no servidor com a origem HTTPS exata do frontend, sem caminho, barra final ou curinga. A API permite preflight restrito e exige Firebase ID token válido para criar ou consultar alertas. CORS não autentica usuários.
  4. Defina a variável pública PAGES_API_BASE_URL do repositório com a origem HTTPS real do backend. Não inclua credenciais, caminho ou parâmetros. Execute novamente o workflow. Sem essa variável, a interface não chama APIs no domínio do Pages.
  5. Para o mapa incorporado, configure GOOGLE_MAPS_BROWSER_KEY no backend e restrinja a chave à API Maps JavaScript e aos referenciadores reais do frontend. O link Google Maps funciona sem chave; GPS depende de permissão.
  6. No servidor, configure TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN e TWILIO_SMS_FROM. Para WhatsApp, use TWILIO_WHATSAPP_FROM e TWILIO_WHATSAPP_CONTENT_SID com modelo aprovado e aceite dos destinatários. O modelo usa {{1}} nome, {{2}} ocorrência e {{3}} mapa ou localização indisponível.
  7. Mantenha LIVE_ALERTS_ENABLED=false até concluir testes com destinatários autorizados. Depois de configurar, cada sessão ainda começa em demonstração; o envio real exige login e ativação explícita.

Resultados e privacidade

Uma solicitação pode estar em processamento, na fila, enviada sem entrega confirmada, entregue, lida, com falha ou com resultado incerto. Demonstração nunca significa entrega. Não há reenvio automático após resultado incerto. O mesmo UUID não reenvia mensagens. O limite é um pedido por 30 segundos e dez por dia por UID; confira status antes de um novo pedido.

Contatos ficam neste navegador, separados pelo caminho e conta, sem sincronização ou criptografia de aplicação. O banco guarda apenas identificadores e resultados por canal, sem corpo de mensagem, telefone ou coordenadas. A limpeza de registros com mais de 24 horas ocorre na próxima criação de alerta. Consulte o README do repositório para todos os detalhes.

Limitações e testes

A interface e os tutoriais ficam em cache após uma primeira visita bem-sucedida. Login, mapas e envios automáticos precisam de internet. O service worker nunca armazena APIs ou tokens. O cache é limitado ao caminho deste aplicativo. SMS manual depende da operadora e confirmação; WhatsApp precisa de conexão.

A PWA não modifica a tela de bloqueio, não usa botões físicos, não garante execução em segundo plano e não aciona serviços públicos automaticamente. O GPS é local e em primeiro plano por até 15 minutos; só posições recentes são usadas nas mensagens. O modo leitura não apaga histórico ou notificações.

npm test usa dados fictícios, SQLite em memória e provedores simulados. Não envia mensagens reais nem faz ligações. Login real, OTP, entrega de mensagens e instalação em aparelho físico precisam de validação específica antes de uso real.
